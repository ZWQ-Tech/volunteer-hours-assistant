01  背景

志愿时长统计，卡在“数据散、口径乱、报表重”

现状问题
  • 记录分散在各班 Excel，字段命名不统一
  • 期末核算需人工筛选、逐人相加，易漏算
  • 每次汇总都要重做一份表，报表格式反复返工
  • 负责人不熟悉公式，操作门槛高
需求提炼

把“按时间段筛选 → 按人汇总 → 出报表”这条固定链路做成一句话可完成的操作， 同时保留可核对的原始明细。

02  方案

用 Agent 承载一条固定业务链路

模型只做两件事：理解用户要什么、决定按什么顺序调用哪个工具。所有计算与文件生成在本地完成， 结果可由原始记录核对。
能力一 · 条件查询

按起止日期检索志愿记录，支持用项目名称进一步筛选。 返回结构化记录，而非自然语言描述。

// 用户 查询 10 月的志愿记录 // 模型决策 query_volunteer_data( "2026-10-01", "2026-10-31")
能力二 · 分组统计

对查询结果按姓名分组，累加时长并统计参与次数， 输出降序排名，用于横向对比。

// 工具内部处理 df.groupby("姓名")["时长"].sum() .sort_values(ascending=False) // 输出 张三 12.5h / 3 次 王五 9.5h / 3 次
能力三 · 导出报表

将统计结果写入 xlsx 并挂到页面下载区， 文件名带时间戳，避免覆盖历史报表。

// 生成文件 志愿时长汇总_20261026_215814.xlsx 工作表：志愿时长汇总 列：姓名 / 总时长 / 参与次数 // 页面即时出现下载按钮

五层结构：界面、会话、模型、工具、数据

04  运行机制

一次“统计并导出”请求的完整时序

三次工具调用由模型自主串联，页面在每一步写入日志，可逐条核对。
01
用户 → 界面
输入“统计 9 月以来每人总时长并导出 Excel”，提交到 st.chat_input
02
Agent → 模型
拼装 system + 历史消息 + tools 定义，发起第一次请求
03
模型 → Agent
返回 finish_reason=tool_calls，指定 query_volunteer_data 与日期参数
04
Agent → 工具
执行查询：过滤 10 条记录中的目标区间，返回 {"status":"success","count":10}
05
Agent → 模型
以 role=tool 回填结果，模型发起第二次调用 calc_total_hours
06
工具内部
按姓名分组累加：张三 12.5 / 王五 9.5 / 李四 8.5 / 赵六 8.5，合计 39.0 小时
07
Agent → 模型
再次回填统计结果，模型发起第三次调用 export_volunteer_excel
08
工具 → 页面
openpyxl 写出 xlsx 字节流，写入会话状态，页面下载区立即出现按钮
09
模型 → 用户
生成中文结论并结束本轮，日志区保留三次调用的入参与结果
全流程约 3 次模型请求，限流时自动退避重试05 / 12

05  工具设计

三个工具的入参与返回

工具入参返回
query_volunteer_data start_date 必填
end_date 必填
project_name 可选 		{ status, count, message, records[] }
status 取值 success / empty / error
calc_total_hours records 可选
省略时取最近一次查询结果		 { status, summary[{姓名, 总时长, 参与次数}], 总计 }
export_volunteer_excel summary 可选
省略时取最近一次统计结果		 { status, filename, message }
Schema 片段（交给模型的定义）
"function": { "name": "query_volunteer_data", "parameters": { "type": "object", "properties": { "start_date": {"type": "string"}, "end_date": {"type": "string"}, "project_name": {"type": "string"} }, "required": ["start_date", "end_date"] } }
三点设计取舍
  • 可选参数：让用户可以不提项目名，模型也能自行补默认行为
  • 数据不回传：统计与导出省略数组参数，避免长 JSON 被截断导致 400 错误
  • 状态三值：success / empty / error 让模型分别给出结果、提示或修正建议
参数由模型生成，但工具内部再做一次日期与类型校验，不信任外部输入。

11  小结

把接口示例做成一个能用的工具

完成的工作
  • 三个自主设计的业务工具
  • 基于真实 Function Calling 的调用链
  • 可演示的界面、日志与结果展示
  • 仓库交付：代码、文档、幻灯片
遇到的问题
  • 模型回传大数组导致参数截断
  • 业务空间限流造成调用中断
  • 编辑器主题与页面配色冲突
均已定位并修复，处理方式见 README。
收获
  • Function Calling 的分工边界
  • 工具参数设计对稳定性的影响更大
  • 异常与边界处理决定能否用于真实业务
