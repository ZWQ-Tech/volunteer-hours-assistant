→
⚙️
代码：真的去干
查表、累加、算距离
生成 Excel

每个数字都从这来
为什么不直接让模型算？它会算错。让模型做加法，等于让它凭感觉报数——汇报里出现的每个数字，必须能回溯到一条真实记录。
约 60 秒，全场最重要一页：这一页讲不清，后面全听不懂。
打个比方：模型是餐厅服务员，负责听懂你要什么、告诉后厨；它不会自己下厨。真正炒菜的是工具。
为什么要这么分？因为大模型最不擅长的就是精确计算。你让它加 20 个小数，它每次结果都不一样。所以我给它划了条线——你只管决定调谁，数字一个都不许你自己编。

04 · 它是怎么跑起来的

一句话，四步，模型全程没算过一个数

模型只做一件事：决定下一步调哪个工具
1
你提需求
"统计 10 月每个人的时长"
模型拆出参数：
2026-10-01 ~ 10-31、全员
2
调查询工具
模型说要调
query_volunteer_data
代码返回 12 条记录
3
调统计工具
模型接着说要调
calc_total_hours
代码算出 4 人排名
4
调导出工具
模型最后说调
export_volunteer_excel
页面弹出下载按钮
三个工具是模型自己串起来的，我没有写"如果用户说了统计就调用统计"这种判断——那样就成假 Agent 了。
约 55 秒：这句话进来之后发生了什么？
模型先理解：时间范围是 10 月 1 号到 31 号，范围是全员。然后它说，我要调查询工具。代码去查，返回 12 条。
模型看到 12 条记录，接着说，我要调统计工具。代码算完给回来。模型再接着说，调导出工具。
整个过程像个传话游戏，但每一棒都是它自己决定交给谁的。

05 · 我做了什么

给项目做了 8 个工具，覆盖三条业务线

前 4 个管"时长账"，第 5、6 个管"找活动"，最后 2 个管"院级汇总"
工具干什么一句话说明
query_volunteer_data按条件查记录按日期、项目名、校内外类型筛出原始记录
calc_total_hours按人汇总时长分组累加，顺带算出每人的校内 / 校外分项
calc_hours_by_type分开算三口径一次给出校内、校外、总计，不让模型自己相加
export_volunteer_excel导出 Excel生成 xlsx 直接挂到页面上，点一下就下载
query_open_activities查志愿活动按省市区查校内校外活动，带距离和报名链接
add_volunteer_record录入新记录说"我昨天干了 3 小时"就能记进去
import_volunteer_excel批量导入加时长负责人上传汇总 Excel，时长自动加到各同学名下
dept_summary院级全员统计人数、总时长、分项、排名一次给齐
名字和参数都是我自己设计的。共同原则：能让工具算的，绝不让模型算；姓名学号不进参数，从绑定账号里取。
约 55 秒：八个工具分三拨看。
前四个是"账本"：查、算、分开算、导出。为什么"分开算"要单独做一个？因为如果让模型先查总数、再自己相减，它就会算错，所以我干脆让工具一次性把三个数字都给它。
中间两个是"找活动"：一个查，一个记。
最后两个是新加的"院级汇总"：负责人把汇总 Excel 传上来，时长自动加到每个同学名下；再一键出全院排名。

06 · 代码看一下

Agent 怎么把一句话变成三个数字

模型只决定"调谁"，所有加减乘除都在工具里——这是 Tool Calling 的核心
# 工具 3 · 校内外分开算三口径（一次给齐，不让模型自己相加）
def calc_hours_by_type(scope="me", start_date=None, end_date=None):
    df = pick_df(scope)                  # 取"本人"或"全员"的真实记录
    df = filter_by_date(df, start_date, end_date)
    on  = df[df["类型"] == "校内"]["时长(小时)"].sum()
    off = df[df["类型"] == "校外"]["时长(小时)"].sum()
    total = on + off
    return {
        "status": "success",
        "校内(小时)": round(on, 1),
        "校外(小时)": round(off, 1),
        "总计(小时)": round(total, 1),
        "占比": {"校内": on/total*100, "校外": off/total*100},
    }
模型念给用户听的是工具返回的 JSON："校内 12.5 小时，校外 3 小时，总计 15.5"。
它不参与加减乘除——这是 Tool Calling 的核心，也是项目区别于"LLM 编故事"的地方。
约 45 秒：左边这个函数是第 3 个工具，叫 calc_hours_by_type。
用户问"我校内校外分别多少"，模型只决定调用这个工具，参数几乎不用传。
里面所有加减乘除都是 pandas 在真实数据上算的——它没机会幻觉。返回的 JSON 模型直接念给用户听就行。
这就是为什么我们敢说"项目里每个数字都能回溯到原始记录"。

07 · 功能一

校内校外分开算，总时长最显眼

学校认定是两套标准，所以页面上必须是三个数字，而不是一个
累计志愿总时长
15.5 小时
校内 12.5h校外 3.0h
校内志愿时长
12.5 小时
校外志愿时长
3.0 小时
志愿记录
4 条
总时长 = 校内 + 校外，三个数字永远对得上；导出的 Excel 里也是三列，不会出现"表里加起来跟页面不一样"。
约 45 秒：这个功能是做到一半才改的。原来只有两张卡：几条记录、多少小时。但真实场景里，校内校外是两套认定标准，混着算没法用。
所以我改成四张卡。最大这张深色的就是总时长，下面一根细条是校内校外的占比，一眼能看出这个人主要在校内还是校外做。
乘一句：这三个数字是互相关联的，总时长一定等于校内加校外，不会打架。

10 · 踩的坑

三个 bug，光看代码发现不了

都是真的跑起来、真的问一遍才暴露的
页面停在上海，问成都却说"没有活动"
原因
工具读的是页面上缓存的活动池
修法
地区不一致就按参数重新生成
只说"武侯区"，第一次总是查不到
原因
模型经常只给区县，不给省市
修法
让它自动反查上一级
成都的活动按"距上海 1700 公里"排序
原因
跨市算距离根本没有意义
修法
同城按距离，跨市改按日期
第三个是最典型的：代码没报错，但答案在业务上是荒谬的。这种问题只能用真实问题去问它才能发现。
约 60 秒，这页最能体现你真做过：重点讲第三个。前两个是技术 bug，第三个是"逻辑上没错但业务上很傻"。
当时我问"成都武侯区有什么活动"，它答得挺像样，但结尾来一句"按距你所在校区由近到远排序"。成都离上海一千七百公里，这个排序毫无意义。
这说明只跑单元测试是不够的，得拿真人会问的话去问它。

11 · 反思

还差什么，下一步做什么

不藏着，这三条是最需要补的
现在还不够的地方
  • 数据只在内存，一重启就没了
  • 没有登录，谁都能改谁的数据
  • 活动是模板生成的，不是真实接口
接下来想做的
  • 接数据库，按学期归档
  • 加登录 + 提交审核流程
  • 对接真实活动源和地图路线
它是一个能跑通全流程的原型，不是能直接上线的系统——这两者之间，差的正是上面这几条。
约 35 秒：这页我讲得快一点。
最大问题是数据没存下来，关掉就没了；其次是没有权限，谁都能改。活动数据也是模拟的。
这几条我心里很清楚，所以没打算把它包装成"成品系统"。
